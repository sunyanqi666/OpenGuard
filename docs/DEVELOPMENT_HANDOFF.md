## 4. 已确定的技术决策

| 决策 | 结论 | 原因 |
| --- | --- | --- |
| 是否整体重写为 Next.js/NestJS | 否 | 保留已有 React + FastAPI 能力，把时间投入真实业务闭环 |
| 第一版 SBOM 格式 | CycloneDX JSON | 结构清晰、生态通用、适合逐步实现 |
| 第一漏洞数据源 | OSV | 可按包生态、名称和版本查询，适合开源依赖场景 |
| AI 产品形态 | 风险详情中的修复助手 | 输入上下文明确，输出可以验证和进入业务流程 |
| AI 是否直接改变风险状态 | 否 | 必须由人工确认，避免模型输出直接成为业务事实 |
| 第一版任务执行方式 | 先同步、后异步 | 先验证数据模型和流程，再引入 Redis/Worker 复杂度 |
| 项目组件与全局组件关系 | 分层建模 | 全局组件是目录，项目组件代表某个项目实际使用的版本 |
| 风险事实来源 | 结构化数据源优先 | AI 负责解释和整理，OSV 等来源负责版本和漏洞事实 |

新增或推翻重要决策时，在本表增加一行，并在开发记录中说明原因与影响。

## 5. 开发记录规范

每次完成一组相关修改，都在“开发记录”顶部追加一个条目。不要只写“优化”或“修复问题”，需要让下一位开发者知道具体行为和边界。

每个条目至少包含：

- 日期和主题。
- 本次目标。
- 修改的功能和关键文件。
- 数据库/API/配置是否发生变化。
- 已完成的验证及结果。
- 尚未完成的事项和已知限制。
- 下一步建议。

```markdown

**目标**

**已完成**

- 用户可以观察到的功能变化。

**关键文件**

- `path/to/file`：说明改动。

**数据与接口变化**

- 新增迁移、接口、字段或配置；没有则写“无”。

**验证**

- `具体命令`：通过/失败及必要说明。

**未完成或限制**

- 剩余工作、已知问题、临时实现。

**下一步**

- 最适合继续的任务。
```

## 7. 常用验证命令

执行测试前先根据 README 创建本地 `.env`。不要将真实密钥提交到仓库。

```bash
# 后端静态检查
docker compose run --rm backend bash scripts/lint.sh

# 后端接口测试
docker compose build backend
docker compose run --rm backend bash scripts/tests-start.sh

# 前端构建
docker compose build backend playwright
docker compose up -d db backend
docker compose run --rm playwright bun run build

# Playwright 端到端测试
docker compose run --rm playwright bunx playwright test --workers=1

# OpenAPI 客户端生成
bash scripts/generate-client.sh
```

每次开发记录应写明实际执行了哪些命令及结果。没有运行的测试不要写成通过。
